# JobPilot — design and functionality

This document describes the application as it works in this repository. `docs/JOBPILOT_DESIGN.md` is the earlier plan. Where the two disagree, this file is the current behavior.

JobPilot is a local, single-user tool. It finds software-engineering jobs, scores them against a private profile, and keeps a short daily list so a person can apply by hand. It never submits an application.

## What it is for

A daily run collects listings, drops poor matches, extracts structure from the job text, and ranks what remains. The person opens Today, reads the job, edits a LaTeX resume, compiles a PDF, and applies on the employer’s site. Applications are tracked afterward: status, applied date, notes, and the job link.

The target in `config.yaml` is a queue of 20 jobs a day and about 25 applications a week. Those numbers are caps, not a promise that 20 good jobs exist.

## What it will not do

- It does not log in to LinkedIn or Naukri, and it does not scrape those sites. Jobs from them arrive only as Gmail alert mail (read-only) or as text the user pastes.
- It does not submit applications, fill employer forms, or click Apply.
- It does not invent experience. `data/profile.yaml` is the source of truth for claims. A project, certification, experiment, or skill being learned is never written as professional experience.
- It does not state more years of experience than `years_for_forms`, invent metrics, or treat the employer as the client.
- It does not guess blank candidate settings (salary, visa, relocation, notice period, and similar). Those stay unset.
- It does not send contact details to the model. Outbound text goes through `llm/redact.py`.
- Secrets stay in `.env`. `data/`, tokens, the resume, and the profile are not committed.
- Tests do not call the network or a real model. Model names, thresholds, caps, and source lists live in `config.yaml`.

## A normal day

1. Start the app with `uv run jobpilot ui`. It serves the built frontend on port 8765.
2. On Run, start the daily pipeline, or run `jobpilot run-daily` from the terminal.
3. The pipeline fetches boards, reads Gmail alerts, analyzes descriptions, scores jobs, builds the queue, and prepares draft notes for the top jobs.
4. Today shows the ranked queue. Open a job, read the description and skill breakdown, edit the resume, compile, and download the PDF.
5. Apply on the career page yourself.
6. On Applications, set the status, applied date, notes, and job link.

One stage failing does not stop the later stages. Each stage is recorded as ok or error.

## Screens

The sidebar is the whole product surface.

| Screen | Route | What it does |
|---|---|---|
| Today | `/` | Ranked queue for the day, progress against the daily and weekly targets, and the selected job. |
| All jobs | `/jobs` | Every posting found so far. Columns are title, company, posted date, location, status, and career link. Filters match location text, posted date, and status. |
| Edit resume | `/resumes` | Edits the base LaTeX resume. It does not load a job. |
| Needs JD | `/needs-jd` | Jobs that matched the filters but arrived with no full description. Paste the posting text here. |
| Applications | `/applications` | Every searched job, with status, dates, notes, the career link, and a place to add a missing description. |
| Answers | `/answers` | Saved replies for personal application-form questions. |
| Stats | `/stats` | Funnel and weekly counts from recorded applied dates. |
| Run | `/run` | Starts the daily pipeline and shows each stage. |
| Profile check | `/profile-check` | Validates `profile.yaml` and `resume_base.yaml` and lists unset settings. |

### Answers

This is where personal form answers are stored: notice period, salary, visa, relocation, and similar questions. Ask the question, and JobPilot answers from the profile when it can. A setting that is still null comes back as NEEDS YOUR INPUT. The reply you type is saved and reused. The page does not submit the form.

### Today

The left column is the ranked queue: company, title, score, and tier. The right column is the job.

- Job description is the cleaned full text. If the source only published a short preview, a note says the rest is not available. The app does not invent the missing text.
- Skills breakdown lists covered, partial, learning, and missing skills, each with a count. If the score lists are empty, names are filled from tags, the profile, and the analysis when that is possible.
- Application drafts show a tailored summary and a short note. With the current config these are written from the profile and the job title. They are not generated by the model.
- Edit resume opens a large dialog: LaTeX on the left, the compiled PDF on the right, Compile, and Download PDF. The job page does not embed a second editor.

### Edit resume

This compiles `data/templates/createResume.tex` and the PDF next to it. The file on disk stays the text you typed. A temporary compile copy is what `pdflatex` sees, so long unbroken words can wrap in the PDF without rewriting the source.

### All jobs

The table lists every posting already stored, including older searches. Columns are job title, company, posted date, location, status, and career link. Status here is the raw pipeline status (`needs_jd`, `filtered_out`, `queued`, and the rest), not the Applications shorthand that shows pre-apply jobs as New.

Location is its own column. The title cell is the role only. LinkedIn alert mail often stores one string, `RoleCompany · City (Remote)Easy Apply`, and leaves `jobs.location` empty. `listing_labels` in `pipeline/labels.py` pulls the city into the location column and, when the company was Unknown, the glued company name into the company column. That split is for display. The stored title, company, and location are not rewritten. Applications uses the same labels, so both screens agree.

Filters:

- Location matches the text shown in the Location column. The match is a case-insensitive substring, so `bengaluru` matches `Bengaluru (On-site)` and `india` matches `Chennai, Tamil Nadu, India`. A city that exists only inside the raw LinkedIn title still matches, because the filter uses the display location rather than the raw `jobs.location` column alone.
- Posted from and posted to bound the calendar date of `posted_at`, or `discovered_at` when the posting date is missing.
- Status matches `jobs.status` exactly.

### Needs JD

Some sources, especially Gmail alerts, store a title and a snippet and leave `description` empty. Those jobs cannot be analyzed or scored until the description exists. Paste the full posting, save it, then run the pipeline again. The job returns to `new` and can be analyzed on the next run.

### Applications

The table fills the page and lists every searched job, including ones with no description. Columns are company and title, posted date, location, JD, status, job link, applied date, and note. A job with no description shows No JD. The edit control on that cell saves the pasted text. Jobs that were waiting on a description go back to `new` so the next pipeline run can analyze them. A job that already has a later status keeps that status.

- Company, title, and location are cleaned for display by `listing_labels`, the same helper All jobs uses. HTML entities are decoded. A Hacker News line that starts with a domain, such as `whitecircle.com/careers, we're…`, is shown as the brand name. A comment that never names a company is shown as Unknown. A LinkedIn title that glues the city on after `·` shows that city in the Location column, not inside the title. The stored row is not rewritten.
- Status choices are New, Applied, Replied, Interview, Offer, and Rejected. Jobs still in the pipeline (`new`, `queued`, `prepared`, and the other pre-apply states) display as New. Changing the status here writes that tracker status directly. It does not stamp an applied date.
- Applied date is a date field. It is empty until you set it. Follow-up highlighting uses this date, and only for jobs whose status is Applied.
- The note and the job link each have an edit control. Saving the link replaces `jobs.url` and `jobs.apply_url`.

### Stats and profile check

Stats count applications from `applications.applied_at`, not from the status column alone. Profile check reports schema problems, claim mismatches, and settings that are still null.

## Pipeline

```text
fetch  →  Gmail alerts  →  analyze  →  score  →  queue  →  prepare
```

`jobpilot run-daily` runs all six. Prepare covers the top `queue.daily_size` jobs (20 unless you pass `--auto-top`).

### Fetch and ingest

Sources are public APIs and feeds, plus read-only Gmail:

- RemoteOK, Remotive, Himalayas (public `https://himalayas.app/jobs/api`, one page), Hacker News “Who is hiring”
- Adzuna for India, with the queries in `config.yaml`
- Greenhouse, Lever, and Ashby boards when tokens are configured
- Gmail messages in the `job-alerts` label, or from the LinkedIn and Naukri sender addresses in config. Instahyre alerts are parsed when the message is from Instahyre or links to `instahyre.com/job-<id>`. Add that From address to `gmail.senders` so unlabeled Instahyre mail is included in the Gmail query.

Each feed is fetched on its own. A source that errors is recorded and the rest continue. The same is true of the Gmail stage: a Gmail failure does not drop jobs already stored by the feed stage.

Each listing becomes a `jobs` row. The fingerprint (normalized company, title, and location) is the cross-source identity. A canonical URL, with tracking parameters removed, is a second lookup when the fingerprint misses. Repeats keep `discovered_at`, refresh `last_seen_at`, and fill `posted_at` only when it was empty. Extra source URLs, and a source job id when the source published one, are stored on `job_urls`. A job with no description that otherwise passes the filter is marked `needs_jd`. A job with a description is `new`.

Title normalization still strips seniority words. That can merge “Java Engineer” and “Senior Java Engineer” at the same company. Changing it would rewrite existing fingerprints, so it is left for a later migration.

Hacker News headers are parsed as `Company | Title | Location`. When the first line is not that shape, the company is taken from a leading domain, or stored as Unknown. HTML in the comment is decoded before that split.

Job description text is cleaned before display: tags stripped, entities decoded, the RemoteOK canary phrase removed, and a truncation note appended when the source text ends early.

### Analyze

The model extracts a structured job: normalized title, seniority, required and preferred skills, location, remote policy, and similar fields. Output is validated with Pydantic before it is stored. The same description is not sent again: analysis is cached by content hash. Contact details are redacted first. The daily call cap in config stops the run before the free-tier limit. A provider failure leaves the job in `new` so a later run can retry it.

### Score

Scoring is ordinary code. The model does not assign the score.

| Part | Points |
|---|---:|
| Skills | 40 |
| Experience | 20 |
| Seniority and title | 15 |
| Location and remote | 15 |
| Extras | 10 |

Skill points depend on evidence level: professional 1.0, project 0.6, certification 0.5, experimental 0.35, learning 0.2, unknown 0. Required skills are most of the skills score; preferred skills are the rest.

A job is not eligible when the posting requires work authorization the profile does not have, or when the role is remote but closed to India and is not in an India city. Blank authorization is not treated as a yes.

Tiers, from `config.yaml`: A at 80 and above, B from 65 up to 80. Jobs older than 21 days that were never applied to are expired.

### Queue

The queue is the highest-scoring eligible jobs, up to `queue.daily_size`, that are not already applied or in a terminal state. Building the queue moves scored jobs to `queued`. A CSV copy can be written under `data/out/`.

### Prepare

Prepare writes an application row: a summary taken from the base resume, a one-line interest note (`I'm interested in the {title} role at {company}.`), and the time it was prepared. The job status becomes `prepared`.

`prepare.llm_tailor_top_n` is 0, so this step does not call the model and does not rewrite the resume. The resume the employer sees is the LaTeX file you compile.

## Resume

The source file is `data/templates/createResume.tex` (the Overleaf Jake resume). It is gitignored with the rest of `data/`.

- The sidebar editor reads and compiles that file.
- Edit resume on a job copies the work into `data/out/resumes/{id}_{company}_{title}.tex` and compiles the PDF beside it.
- Compile runs `pdflatex` with `-interaction=nonstopmode -halt-on-error -no-shell-escape`. On macOS the binary is also looked up at `/Library/TeX/texbin/pdflatex` when it is not on `PATH`.
- The PDF preview is served inline from the app. Download uses `?download=1`.
- Word wrap for long tokens is applied only to the compile copy. The editor file stays as typed.

## Status

Two layers exist.

The pipeline uses a fixed graph in `tracking/status.py`: `new`, `needs_jd`, `analyzed`, `scored`, `queued`, `prepared`, then `applied`, `replied`, `interview`, `offer`, `rejected`, plus `skipped`, `expired`, and `filtered_out`. `jobpilot mark` and Today’s “Mark applied” follow that graph. Marking Applied through that path records `applied_at` if it was empty.

The Applications screen is a tracker. It shows pre-apply jobs as New and lets you set New, Applied, Replied, Interview, Offer, or Rejected without walking the graph. That update does not fill the applied date for you.

## Data

SQLite file: `data/jobpilot.db`. No ORM.

| Table | Holds |
|---|---|
| `jobs` | Listing, URL, description, status |
| `analyses` | Validated model extraction, keyed by content hash |
| `scores` | Component scores, tier, matched and missing skills |
| `applications` | Summary, note, prepared time, applied date, notes, resume paths |
| `answer_bank` | Saved answers for the CLI `answer` command |
| `api_budget` | Count of model and Adzuna calls |
| `company_boards` | Discovered Greenhouse, Lever, and Ashby boards |

`data/profile.yaml` is the candidate: titles, years, skills with evidence level, location, and settings that may be null. `data/resume_base.yaml` is the bullet bank used when a summary is assembled. The PDF resume is the LaTeX template, not that YAML file.

## Configuration

`config.yaml` holds model ids, the daily model cap (20), tier cutoffs (80 and 65), max job age (21 days), queue size (20), weekly target (25), which sources are on, Adzuna queries, and follow-up age (7 days). `.env` holds `GEMINI_API_KEY` and the Gmail OAuth client file. The UI token is `JOBPILOT_DEV_TOKEN` in development, or a generated token injected into the page otherwise. Mutating API calls send `X-JobPilot-Token`.

## Stack

Python 3.12, uv, Typer, Pydantic v2, stdlib sqlite3, httpx, FastAPI for the local API. The UI is React 18, TypeScript, and Vite. `jobpilot ui` serves `frontend/dist`. Tests are pytest and vitest. Ruff checks the Python.

## How this differs from the original plan

The original plan drafted resume summaries with the model for tier A, and it assumed a terminal-only app with Streamlit as a later idea. The current app is a local web UI. Resume text is the LaTeX file you edit and compile. Prepare does not call the model. LinkedIn and Naukri are still alert-mail only.
